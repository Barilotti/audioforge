# ADR-0017: Бенчмарки движка и порог регрессии в CI (S2.5)

- **Статус:** принято
- **Дата:** 2026-11-18
- **Связано:** архитектура v0.2 разделы 7.2 (S2.5, S10.4) и риск R8; реализовано в S2.5

## Контекст
Нагрузка растёт с числом слоёв (риск R8). Нужно замечать замедление движка в том же PR, где оно появилось, а не на приёмке S10.4. Раннеры GitHub Actions бывают разной скорости, поэтому абсолютное время в микросекундах между запусками сравнивать нельзя.

## Решение
- **Google Benchmark 1.9.1** через CPM, цель `af_benchmarks` в папке `benchmarks/`. Собирается при `AF_BUILD_BENCHMARKS=ON` (пресеты `linux-clang-release` и `windows-msvc`).
- **Сценарии:**
  - `BM_Engine64Layers/{128,256,512}`: 64 стереослоя по минуте (15 клипов по 4 с с фейдами 10 мс), источники 48 кГц, без ресемплинга. Один блок `AudioEngine::process` на итерацию.
  - `BM_Engine64LayersResampled/{128,512}`: то же с источниками 44,1 кГц, каждый голос ресемплирует sinc-ядром (качество «как экспорт»).
  - `BM_Compile64Layers`: компиляция графа 64 слоёв (платится при каждой правке).
  - `BM_PeakBuildOneMinute`: построение пиков минуты стерео.
  - `BM_Calibration`: фиксированная скалярная нагрузка, эталон скорости машины.
- **Нормализация:** каждое время (медиана из 5 повторов) делится на время `BM_Calibration` того же запуска. Базовая линия хранит эти отношения: `benchmarks/baseline/linux-ci.json`.
- **Базовая линия — верхняя граница нескольких прогонов CI.** Раннеры GitHub попадают на разные модели CPU, и даже после нормализации отношения одного и того же кода расходятся до ±30 % (сильнее всего у компиляции графа, она упирается в выделение памяти). Поэтому для каждого бенчмарка берётся наибольшее отношение из прогонов CI.
- **Порог:** `benchmarks/check_regression.py` валит CI, если отношение выросло больше чем на 25 %. Порог записан в файле базовой линии. Скрипт печатает и нагрузку движка: время блока, делённое на длительность блока.
- **Где проверяется:** job `linux-clang-release`. Windows release запускает бенчмарки только для отчёта. Оба отчёта JSON сохраняются как артефакты CI.
- **Обновление базовой линии:** только намеренно, отдельным коммитом с объяснением (например, ресемплер стал качественнее и дороже). Порядок описан в `docs/testing/benchmarks.md`.

## Последствия
- Базовая линия на момент S2.5 (локальная машина, один поток): 64 слоя без ресемплинга занимают около 1,5 % длительности блока при 128 сэмплах; с ресемплингом около 40 %. Значит, ресемплинг стоит в 25–30 раз дороже чтения, и при 64 слоях 44,1 кГц на устройстве 48 кГц запас по CPU невелик. Варианты на будущее: ресемплинг при импорте или кэширование ресемплированного звука, SIMD в ядре, качество `draft` для тяжёлых проектов, параллельный рендер (раздел 4.5, риск R8). Бюджет CPU согласуется к S10.4.
- Бенчмарки добавляют к job `linux-clang-release` около минуты.
- Сравнение через эталон снижает зависимость от скорости раннера, но не убирает разницу архитектур CPU. Вместе с верхней границей прогонов проверка надёжно ловит замедление примерно от 1,5 раза; мелкие замедления на 10–20 % она не заметит. Если этого окажется мало, следующий шаг — A/B: в том же job собрать базовую ветку и сравнить два прогона на одной машине.

## Рассмотренные альтернативы
- **Абсолютные пороги в микросекундах.** Ложные срабатывания на медленных раннерах или пропуск регрессий на быстрых.
- **Сравнение с main в том же job.** Точнее, но вдвое дольше сборка и запуск; можно добавить позже, если 25 % окажется слишком грубо.
- **Отдельный раннер для бенчмарков.** Самый стабильный вариант, но требует своей машины.
