## 0. Краткое резюме

- **Один процесс, один язык, один фреймворк:** C++20 + JUCE 8 (UI, аудио, форматы, DSP), сборка CMake.
- **Ядро отделено от UI.** Доменная модель, сериализация, DSP и рендер-движок собираются и тестируются без окна, в том числе на Linux в CI.
- **Модель проекта неизменяемая** со структурным разделением. Отсюда Undo/Redo, потокобезопасные снимки для автосохранения и компиляции графа.
- **Аудиодвижок получает скомпилированный RenderGraph** через почтовый ящик из одного атомарного указателя. В real-time callback нет аллокаций, блокировок, ввода-вывода и освобождения памяти. Ни одна очередь при переполнении не блокирует аудиопоток и не теряет граф.
- **Сигнал проходит три уровня эффектов:** Clip FX → Layer FX → Group/Bus FX → Master FX, с единым интерфейсом процессора, компенсацией задержки и хвостами эффектов.
- **Preview и экспорт идут через один код рендеринга.** Режим Preview «Как экспорт» по умолчанию даёт тот же результат, что и финальный рендер; расхождения возможны только в явно перечисленных случаях.
- **Проект — JSON-файл с версией схемы и миграциями.** Время на таймлайне хранится целым числом тиков (1/705 600 000 с) в пределах ±2^53, поэтому точно читается любым JSON-парсером.
- **Phase 1 идёт вертикальными этапами S0–S10.** После каждого этапа есть установимая сборка, которой можно пользоваться.

### 1.2 Ключевые архитектурные принципы

1. **Направление зависимостей строго сверху вниз.** `af_model`, `af_dsp`, `af_core` ничего не знают об UI, об аудиоустройствах и о файлах проекта. Правило проверяется в CMake (target-зависимости), нарушение не соберётся.
2. **Модель — единственный источник истины.** UI не хранит «свою» копию состояния (кроме чисто визуального: зум, скролл, выделение). Движок хранит только скомпилированное представление модели.
3. **Все изменения проходят через Commands.** Нет способа изменить проект в обход истории Undo. Это касается и «умных» операций будущих фаз (Smart Alignment, Procedural Engine).
4. **Тяжёлая работа уходит с message thread.** Декодирование, пики, анализ, экспорт, автосохранение, индексация библиотеки выполняются в `JobScheduler` (пул потоков с приоритетами и отменой).
5. **Расширяемость через реестры, а не через `switch`.** Эффекты DSP, форматы импорта, профили экспорта, Workspaces регистрируются в реестрах (`ProcessorRegistry`, `DecoderRegistry` и т. д.). Новый инструмент добавляется без правки ядра (принцип 6 ТЗ).
6. **Workspaces — это UI + сервисы поверх общего ядра**, а не отдельные движки (раздел 5 ТЗ). Foley Designer, Ambience Designer и другие генерируют и редактируют ту же модель Event/Layer/Clip.

### 1.3 Доменная модель

Пять сущностей ТЗ сохраняются, но с одним важным уточнением.

**Уточнение к ТЗ (Layer и Clip).** В ТЗ Layer одновременно и клип (asset, in/out, fade, reverse), и канал (mute/solo, pan, цепочка обработки). Это перестаёт работать при первой же операции **Split**: разрезанный слой должен остаться одним слоем с двумя кусками, иначе количество слоёв бесконечно растёт, и группировка, mute/solo, цепочка эффектов дублируются. Предлагается:

- **Layer** — строка на таймлайне (то, что пользователь называет слоем): имя, цвет, gain, pan, mute/solo, цепочка обработки, автоматизация, принадлежность группе.
- **Clip** — фрагмент материала внутри слоя: ссылка на Asset, позиция, source in/out, clip gain, fade in/out с формой кривой, reverse, (Phase 2) pitch/stretch.

Слой с одним клипом в точности совпадает с Layer из ТЗ, поэтому для пользователя ничего не меняется, а архитектура выдерживает Split, Duplicate и будущие Round Robin-слоты.

```
Project
 ├─ ProjectSettings (sample rate проекта, tempo/grid, export profiles)
 ├─ AssetTable            id → AssetRef (пути, fingerprint, кэш метаданных)
 ├─ Events[]              ← Phase 1: в UI открыт один Event, модель уже поддерживает много
 │    ├─ EventSettings, Metadata
 │    ├─ Groups[]  (дерево; Group = шина: gain, pan, mute/solo, chain)
 │    ├─ Layers[]  (порядок, groupId, параметры канала, chain, automation)
 │    │    └─ Clips[]
 │    ├─ Markers[], LoopRegion
 │    └─ MasterBus
 ├─ Recipes[]   (Phase 2: шаблон Event со «слотами» для ассетов и правилами рандомизации)
 └─ Scenes[]    (Phase 3: размещение экземпляров Events, источники, расписание)
```

- **Recipe** использует ту же схему, что и Event, плюс слоты замены ассетов, правила рандомизации и историю версий. Event ↔ Recipe конвертируются без потерь.
- **Scene** размещает экземпляры Events (а не копии), поэтому изменения Event видны во всех сценах.
- **Идентификаторы:** UUID v4/v7 для всех сущностей. Ссылки только по ID, не по индексам. Это нужно для Undo, слияния, миграций и стабильности состояния DSP при пересборке графа.
- **Время:** `TimeTicks` (int64), 1 тик = 1/705 600 000 с. Число делится без остатка на 44 100, 48 000, 88 200, 96 000, 176 400, 192 000, поэтому позиции точно переводятся в сэмплы любого стандартного sample rate. Позиции внутри исходного файла хранятся в сэмплах файла, а допустимый диапазон и правила записи в JSON описаны в разделе 5.3.

### 1.4 Неизменяемая модель, Commands и Undo

- Узлы модели — `std::shared_ptr<const T>`. Правка создаёт новые копии только изменённых узлов и их предков, остальное разделяется (структурное разделение). Если профилирование покажет необходимость, коллекции переводятся на persistent-контейнеры (библиотека `immer`, Boost License).
- `Command` — чистая функция `Document → Result<Document>` с именем для меню Undo и валидацией входа.
- `Transaction` объединяет несколько команд в один шаг истории. Непрерывные жесты (перетаскивание клипа, движение фейдера) коалесцируются в одну запись.
- `UndoHistory` хранит корни документов. Undo = вернуть предыдущий корень, операция O(1) и не может «сломаться», в отличие от ручных `revert()`.
- `ProjectSession` после коммита рассылает уведомление `DocumentChanged(old, new, changeSet)`. UI перерисовывает только затронутое, движок перекомпилирует граф, автосохранение помечает проект грязным.

### 3.2 Где рекомендация расходится с ТЗ и почему

ТЗ просит объяснять противоречия, поэтому перечисляю их явно.

**1. Qt / C++ для UI → JUCE UI.**
- Qt + JUCE в одном процессе — это два цикла событий и два «message thread», две системы окон и событий мыши, две системы потоков и таймеров. Их стыковка работает, но требует постоянного обслуживания и даёт трудноуловимые ошибки (фокус, DPI, drag & drop, модальные окна).
- Аудиоспецифичные виджеты (таймлайн, waveform, фейдеры, метры) в обоих случаях пишутся с нуля. Стандартные Qt-виджеты дают мало выигрыша для такого приложения.
- Лицензирование усложняется: Qt под LGPL требует динамической линковки и соблюдения условий, коммерческий Qt дорог. Плюс отдельная лицензия JUCE.
- JUCE GUI проверен на полноценных DAW (например, Tracktion Waveform построен на JUCE).
- **Чем мы платим:** в JUCE нет готового docking (аналога Qt Advanced Docking System). В Phase 1 делаем резиновые панели с сохранением Layout Presets (этого достаточно по разделу 11 ТЗ), полноценный docking пишем позже как отдельный модуль.
- **Страховка:** UI отделён от ядра. Если однажды понадобится Qt, переписывается только `af_ui`, ядро остаётся.

**2. PySide6 для прототипа → не делаем.** Прототип на Python станет выброшенным кодом: real-time аудио в Python невозможно из-за GIL и сборщика мусора, а значит фундаментальная часть (движок) в прототипе не проверяется. Цель «фундамент, а не макет» прямо противоречит прототипу.

**3. NumPy + librosa для анализа → нативный C++.** Встраивание Python-рантайма в Windows-приложение — это упаковка интерпретатора, сотни мегабайт, медленный старт, хрупкие зависимости и межпроцессный обмен буферами. Нужный анализ (onset/spectral flux, пики, RMS, LUFS, crest factor, тишина, клиппинг, спектр) реализуется на C++ за разумное время и работает в том же процессе с теми же буферами. Для будущего ML используется ONNX Runtime. Python остаётся инструментом для исследований вне продукта.

**4. libsndfile → декодеры JUCE за интерфейсом `IAudioDecoder`.** JUCE уже читает WAV (включая BWF-метаданные), AIFF, FLAC, MP3, Ogg. libsndfile под LGPL потребовал бы динамической линковки и не добавил бы форматов, нужных в Phase 1. Если позже понадобится (например, для экзотических форматов), он подключается как ещё один декодер в реестре.

**5. Custom Qt Widgets / OpenGL → JUCE Graphics (Direct2D на Windows).** OpenGL в JUCE устарел как путь рендеринга UI. Direct2D в JUCE 8 даёт аппаратное ускорение без отдельного GL-контекста. Waveform рисуется из многоуровневых пиков, поэтому нагрузка на рендер небольшая.

**6. «JSON + SQLite для проекта» → JSON для проекта, SQLite позже и только для библиотеки.** Проект — это дерево, которое целиком загружается в память и целиком сохраняется. SQLite здесь добавляет сложность без выгоды. SQLite оправдан там, где нужны индексы и поиск по тегам: он появится вместе с ними, не раньше Phase 2 (раздел 5.4).

### 3.3 Лицензии

На время разработки используется бесплатный коммерческий уровень JUCE (Starter) и драйвер WASAPI. Проверка коммерческой лицензии JUCE, условий ASIO SDK и других юридических вопросов вынесена в отдельный список решений перед публичным релизом (раздел 10).

Остальные зависимости подобраны с разрешительными лицензиями (MIT/BSD/BSL/public domain), чтобы не ограничивать будущую модель распространения.

## 4. Audio Engine и взаимодействие с UI

### 4.1 Потоки

| Поток | Что делает | Что запрещено |
|---|---|---|
| **Message thread (UI)** | Ввод, Commands, отрисовка, публикация графов, освобождение отработавших графов | Декодирование, анализ, экспорт, файловый I/O дольше нескольких мс |
| **Audio thread (RT)** | `audioDeviceIOCallback`: забрать новый граф, применить параметры и команды транспорта, отрендерить блок, опубликовать позицию и метры | Аллокации, освобождение памяти (в том числе последнего `shared_ptr`), мьютексы, ожидание, I/O, логирование, исключения, системные вызовы |
| **Graph compiler** (задача в worker pool) | Компиляция RenderGraph из снимка документа, подготовка процессоров (`prepare`, аллокации разрешены) | Доступ к UI-компонентам |
| **Worker pool** | Декодирование, пики, анализ, экспорт, точный Preview (4.5) | Доступ к UI-компонентам |
| **IO thread** | Автосохранение, бэкапы, запись кэшей | |

### 4.2 Передача RenderGraph между потоками

#### Владение

У каждого графа в любой момент ровно один владелец, и владение передаётся по цепочке:

```
 Compiler ─► Message thread ─► Mailbox ─► Audio thread (current) ─► RetireQueue ─► Message thread ─► delete
  (unique_ptr)                 (atomic ptr)    (raw ptr)               (SPSC, raw ptr)    (unique_ptr)
```

- `RenderGraph` неизменяем после компиляции, кроме состояния DSP, которое меняет только аудиопоток.
- Граф держит `shared_ptr` на буферы ассетов и на объекты процессоров. Поэтому удаление графа на message thread — единственное место, где могут освободиться буфер ассета или процессор. Аудиопоток никогда не уменьшает счётчики ссылок.
- Каждый граф имеет возрастающий номер поколения `generation`.

#### Почтовый ящик (UI → RT)

Вместо очереди графов используется **почтовый ящик на один элемент** с правилом «новейший побеждает»: `std::atomic<RenderGraph*> mailbox`.

```cpp
// Message thread: публикация нового графа
void Engine::publish(std::unique_ptr<RenderGraph> g) {
    RenderGraph* stale = mailbox.exchange(g.release(), std::memory_order_acq_rel);
    delete stale;   // аудиопоток этот граф не забирал и уже не заберёт: удалять безопасно
}

// Audio thread: начало каждого блока
void Engine::acquirePending() noexcept {
    if (retireQueue.freeSlots() == 0) { ++stats.deferredSwaps; return; } // см. переполнение
    if (RenderGraph* next = mailbox.exchange(nullptr, std::memory_order_acq_rel)) {
        beginSwap(current, next);          // мгновенно или через кроссфейд (ниже)
    }
}
```

- Почтовый ящик **не может переполниться**: если UI опубликовал три графа, пока аудиопоток обрабатывал один блок, промежуточные два удаляются на message thread, а аудиопоток получает последний. Промежуточные состояния не нужны: важно только самое свежее.
- `exchange` атомарен, поэтому граф либо забран аудиопотоком, либо возвращён message thread, но никогда не оказывается у обоих.

#### RetireQueue (RT → UI)

- Lock-free SPSC-очередь фиксированной ёмкости (64 указателя, память выделена заранее).
- После завершения подмены аудиопоток кладёт старый граф в RetireQueue. Message thread по таймеру (30 Гц) и при каждом `publish` забирает графы и удаляет их.
- Аудиопоток публикует `appliedGeneration` (атомик): номер графа, который реально звучит. По нему UI и `ProjectSession` знают, когда правка стала слышна.

#### Переполнение: правила для каждого канала

| Канал | Направление | Структура | Что происходит при переполнении |
|---|---|---|---|
| Графы | UI → RT | Почтовый ящик на 1 элемент | Не переполняется: старый неподобранный граф удаляется на UI |
| Отработавшие графы | RT → UI | SPSC, 64 | Аудиопоток **не начинает подмену**, пока нет свободного слота: продолжает играть текущий граф, новый остаётся в почтовом ящике, растёт счётчик `deferredSwaps`. Граф не теряется, память на RT не освобождается. Подмена произойдёт в первом блоке после того, как UI освободит место. На практике очередь заполняется только если message thread заморожен (отладчик, зависание), и тогда отставание звука от правок — правильное поведение |
| Непрерывные параметры (gain, pan, bypass) | UI → RT | `ParameterBank`: массив атомарных значений по слотам + атомарная «грязная» битовая маска | Не переполняется: хранится только последнее значение каждого параметра |
| Команды транспорта (play, stop, seek, loop) | UI → RT | SPSC, 256 | `push` на UI не блокирует; при неудаче команда остаётся в локальной очереди UI и повторяется в следующем тике таймера. Транспорт дополнительно хранит «желаемое состояние», поэтому повтор идемпотентен |
| Позиция, состояние, метры | RT → UI | Атомики и triple buffer | Не переполняется: UI читает последнее значение |
| События (xrun, конец воспроизведения, достигнут конец loop) | RT → UI | SPSC, 256 | Событие отбрасывается, растёт счётчик `droppedEvents`. Ни одно из этих событий не влияет на корректность: состояние транспорта всё равно публикуется через атомики |

Счётчики `deferredSwaps`, `droppedEvents`, `xruns` показываются в окне диагностики и пишутся в журнал. В тестах заполнение очередей проверяется принудительно.

#### Подмена без щелчков и сохранение состояния DSP

- **Состояние DSP живёт отдельно от графа.** Каждый процессор и каждая шина имеют стабильный `NodeId` (из ID клипа, слоя, группы, эффекта). Компилятор берёт существующие объекты состояния (фильтры, линии задержки, хвосты реверберации, сглаживатели) из `NodeStateStore` по `NodeId` и создаёт новые только для новых узлов. Два графа могут ссылаться на одно состояние, но меняет его только аудиопоток и только из текущего графа, поэтому гонок нет. Правка одного слоя не сбрасывает реверберацию в других.
- **Структурная правка в зоне воспроизведения** (удалён или сдвинут клип под playhead, изменён порядок эффектов, включён bypass): компилятор помечает граф флагом `needsCrossfade`. Аудиопоток в течение 256 сэмплов рендерит старый и новый граф и делает равномощный кроссфейд, затем отправляет старый в RetireQueue. Буферы для этого выделены в каждом графе заранее. Остальные правки подменяются мгновенно на границе блока.
- **Sample rate и максимальный размер блока** записаны в граф. Граф, скомпилированный под другие параметры устройства, аудиопоток не принимает: он сразу уходит в RetireQueue, а UI получает событие на перекомпиляцию.

#### Смена устройства

JUCE гарантирует, что `audioDeviceStopped()` и `audioDeviceAboutToStart()` вызываются, когда callback не выполняется. В этот момент движок забирает текущий граф и все графы из почтового ящика и RetireQueue в собственность message thread, сбрасывает `current = nullptr` (аудиопоток выдаёт тишину с коротким затуханием), и после старта устройства компилирует граф под новые sample rate и размер блока. Пропажа устройства обрабатывается так же, плюс транспорт останавливается.

#### Закрытие проекта

Последовательность выполняется `ProjectSession::close()` как асинхронная машина состояний на message thread, UI при этом не замирает:

1. Если есть несохранённые изменения, спросить пользователя (до любых действий).
2. Транспорт: команда Stop с затуханием 10 мс.
3. Опубликовать **пустой граф** (тишина, без ссылок на ассеты) с номером `G`.
4. Дождаться `appliedGeneration >= G` (проверка по таймеру). Если устройство не запущено или callback не вызывается дольше 200 мс, остановить устройство и забрать текущий граф напрямую: после остановки callback гарантированно не выполняется.
5. Очистить RetireQueue и почтовый ящик, удалить графы.
6. Отменить фоновые задачи проекта (токены отмены) и дождаться их завершения. Задачи экспорта прерываются, незаконченные файлы удаляются.
7. Освободить записи `AudioBufferCache`, `NodeStateStore` и кэш пиков, принадлежащие проекту.
8. Удалить lock-файл, уничтожить `ProjectSession`.

#### Завершение приложения

1. Закрыть проект по шагам выше (включая вопрос о несохранённых изменениях; отказ пользователя отменяет выход).
2. Закрыть аудиоустройство (`AudioDeviceManager::closeAudioDevice`, синхронно останавливает callback).
3. Забрать у движка все оставшиеся графы, очистить очереди.
4. Остановить `JobScheduler`: отменить задачи, ждать до 3 с; задачи, не ответившие на отмену, логируются (это ошибка, которую мы исправляем, а не маскируем).
5. Завершить IO-поток после записи настроек и журнала.
6. Уничтожить сервисы в порядке, обратном созданию (порядок зафиксирован в `Application` и покрыт тестом запуска и выхода в CI).

Аварийное завершение не проходит эти шаги. Для этого есть автосохранение и восстановление (раздел 5.6).

### 4.3 Путь от правки к звуку

```
 UI жест ──► Command ──► ProjectSession.commit() ──► новый Document
                                   │
                                   ├─► UI: DocumentChanged → перерисовка
                                   │
                                   └─► GraphCompiler (worker) → unique_ptr<RenderGraph>
                                             │ publish() на message thread
                                             ▼
                                   Mailbox ─► Audio thread: подмена на границе блока
```

- **Быстрые параметры не пересобирают граф.** Во время движения фейдера значение идёт в `ParameterBank`, на аудиопотоке попадает в `SmoothedValue` (рампа 5–20 мс). В модель значение коммитится одной транзакцией в конце жеста.
- **Компиляция дебаунсится:** если документ изменился, пока граф компилируется, следующая компиляция берёт самый свежий снимок, промежуточные пропускаются.
- **Транспорт и позиция:** UI читает позицию и метры с частотой экрана (`VBlankAttachment`).
- **Предпрослушивание из Sample Browser** идёт через отдельную шину Preview того же движка (4.4), без второго устройства.

### 4.4 Эффекты: Clip FX, Layer FX, Group/Bus FX

#### Порядок прохождения сигнала

```
CLIP (на каждый клип)
  Source read (буфер ассета, source in/out, выбор каналов, reverse = чтение назад)
   → Resample / Varispeed (к частоте рендера; Phase 2: Pitch и Time Stretch)
   → Fade In / Fade Out (огибающая на границах материала)
   → Clip Gain (действует как входной уровень для нелинейных эффектов)
   → [Clip FX chain]  ── может звучать после конца клипа (хвост)
   → в сумму слоя
LAYER
  Σ клипов слоя
   → [Layer FX chain] (pre-fader inserts)
   → Layer Gain (фейдер, сглаживание)
   → Pan (mono-источник: constant-power −3 дБ; stereo: balance)
   → Mute / Solo (с рампой)
   → Meter (post-fader)
   → (Phase 2: post-fader sends на Aux-шины)
   → в родительскую группу или Master
GROUP / BUS (вложенные группы и Aux-шины)
  Σ дочерних слоёв и групп
   → [Group FX chain] → Gain → Pan → Mute / Solo → Meter → в родителя
MASTER
  Σ верхнего уровня → [Master FX chain] → Master Gain → Meter → Output

ТОЛЬКО ЭКСПОРТ (после Master, вне графа)
  Normalization (peak / loudness) → Dither (при понижении разрядности) → Encoder

PREVIEW-шина (Sample Browser) → смешивается после Master Gain, мимо Master FX
```

Почему именно так:

- **Fade до Clip FX.** Fade описывает, где материал начинается и заканчивается. Если поставить его после нелинейных эффектов, жёсткий срез исходника попадёт в дисторшн и даст щелчок. Хвосты эффектов при этом сохраняются: см. «Хвосты» ниже.
- **Clip Gain до Clip FX.** Так им можно управлять входным уровнем сатурации и компрессора, как в звукорежиссёрской практике. Выходной уровень клипа задаётся утилитой Gain в конце цепочки.
- **Layer FX до фейдера.** Фейдер и панорама не должны менять то, как сработает компрессор слоя.
- **Нормализация и дизер вне графа.** Это свойства файла экспорта, а не звука проекта; они не должны попадать в Preview по умолчанию (см. 4.5).

#### Единый интерфейс процессора

Все три уровня используют один интерфейс, поэтому любой эффект можно поставить в любую цепочку:

```cpp
class IProcessor {
public:
    virtual ProcessorInfo info() const = 0;                 // id типа, версия алгоритма, параметры
    virtual void prepare(const ProcessSpec&) = 0;           // non-RT: sampleRate, maxBlock, каналы; аллокации тут
    virtual void process(ProcessContext&) noexcept = 0;     // RT: никаких аллокаций и блокировок
    virtual void reset() noexcept = 0;                      // сброс состояния (seek, stop)
    virtual int  latencySamples() const noexcept = 0;
    virtual TailLength tail() const noexcept = 0;           // 0, конечная длина или «до тишины»
    virtual void saveState(StateWriter&) const = 0;         // non-RT, для проекта
    virtual void loadState(const StateReader&) = 0;
};
```

- **Цепочка** — упорядоченный список экземпляров процессоров с `bypass`, `mix` (dry/wet) и стабильным ID. Bypass переключается кроссфейдом ~10 мс. Изменение порядка — структурная правка (новый граф с кроссфейдом), состояние процессоров сохраняется по ID.
- **Реестр процессоров** (`ProcessorRegistry`): встроенные эффекты DSP Laboratory, а в Phase 4 — обёртка VST3 за тем же интерфейсом. Версия алгоритма записывается в проект, чтобы старые проекты звучали так же после обновлений (новая версия алгоритма = новый тип или явная миграция).
- **Компенсация задержки (PDC).** Процессоры сообщают задержку (lookahead-лимитер, линейно-фазовый EQ, pitch shifter). Компилятор вычисляет задержку каждой ветки и выравнивает параллельные ветки линиями задержки перед суммированием, а транспорт сдвигает чтение клипов. Встроенные эффекты Phase 1 без задержки, но механизм и тесты есть с самого начала, потому что добавить его позже в работающий граф дорого.
- **Хвосты.** Голос клипа остаётся активным после конца клипа, пока не закончится хвост его цепочки (или сигнал не опустится ниже −96 дБ дольше 100 мс). Цепочки слоёв, групп и Master работают всё время воспроизведения. Длина экспорта по умолчанию: «до затухания хвоста», с ограничением (по умолчанию 10 с) и ручной настройкой.
- **Seek и старт воспроизведения** вызывают `reset()` у процессоров с состоянием, а затем, при включённом «точном старте», состояние восстанавливается прогоном (см. 4.5).
- **Стоимость Clip FX.** У каждого клипа свои экземпляры. Неактивные голоса (вне клипа и без хвоста) не обрабатываются. Если клип со сложной цепочкой не меняется, его можно «заморозить» (Phase 2): результат рендерится в кэш и проигрывается как обычный буфер.
- **Phase 1:** структура цепочек есть в модели, сериализации, графе и UI на всех трёх уровнях, но в реестре только утилиты Gain и Polarity/Channel (для тестов маршрутизации, PDC и хвостов это достаточно). Полный набор эффектов DSP Laboratory — Phase 2.
- **Каналы.** В Phase 1 шины внутри графа стерео. Тип `ChannelLayout` присутствует в API с первого дня, чтобы в Phase 4 (Spatial Audio) добавить многоканальные шины без переписывания интерфейсов.

### 4.5 Preview Quality и Render Quality

#### Главное правило

Есть один код рендеринга и один набор алгоритмов. Preview и экспорт различаются только параметрами из `RenderSpec`, и каждый такой параметр перечислен явно:

| Параметр | Draft | **Как экспорт** (Preview по умолчанию) | Final (экспорт) |
|---|---|---|---|
| Ресемплинг ассетов | Кубическая интерполяция | Polyphase windowed-sinc, высокое качество | Тот же, что в «Как экспорт» |
| Pitch / Time Stretch (Phase 2) | Быстрый режим | Режим высокого качества | Режим высокого качества |
| Оверсэмплинг нелинейных эффектов (Phase 2) | 1× | Как в настройках эффекта | Как в настройках эффекта |
| Состояние эффектов при старте не с начала | Сброс | **Точный старт:** прогон от начала Event до позиции | Рендер всегда с начала |
| Нормализация | Нет | Опция «Слушать с нормализацией» | По профилю экспорта |
| Дизер | Нет | Нет (слышен только при 16 бит) | По профилю экспорта |
| Частота рендера | Частота устройства | Частота устройства | Частота экспорта |

**Draft** нужен только как аварийный режим для очень тяжёлых проектов на слабой машине. По умолчанию Preview работает в режиме **«Как экспорт»**.

#### Гарантии, проверяемые тестами

1. **Независимость от размера блока.** Выход графа одинаков при любом разбиении на блоки (тест: случайные размеры блоков против фиксированного, сравнение бит-в-бит). Отсюда: Preview на устройстве с любым buffer size = офлайн-рендер с той же частотой.
2. **Независимость от точки старта.** Модуляторы, LFO и случайные значения зависят от позиции на таймлайне и seed, а не от момента нажатия Play.
3. **Preview «Как экспорт» при частоте устройства = частоте экспорта даёт тот же сигнал, что Final до этапов нормализации и дизера.** Тест сравнивает офлайн-рендер в режиме Preview и экспорт: разница должна быть нулевой.

#### Точный старт

Для эффектов с состоянием (реверберация, задержка, компрессор) старт из середины даёт не тот звук, что в экспорте: хвостов от предыдущих клипов ещё нет. В режиме «Как экспорт» при старте с позиции P движок в фоне прогоняет граф от начала Event до P быстрее реального времени и начинает воспроизведение с готовым состоянием. Для типичных звуковых событий длиной в секунды это занимает миллисекунды. Точный старт выполняется **автоматически**, если прогон укладывается в бюджет подготовки (по умолчанию 150 мс, настраивается). Если не укладывается (длинные амбиенсы), воспроизведение начинается сразу без прогона, и приложение **явно** показывает, что старт приблизительный: индикатор в транспорте и подсказка с предложением Render Preview. Render Preview остаётся способом гарантированно получить точное прослушивание.

#### Когда реальное время не справляется

Если в режиме «Как экспорт» загрузка аудиопотока превышает бюджет (по умолчанию 70%), движок не снижает качество молча. Пользователь видит предупреждение и выбирает:

- **Точное прослушивание (Render Preview):** Event или выделенный диапазон рендерится в фоне в качестве Final, затем проигрывается готовый буфер. Это результат, совпадающий с экспортом бит-в-бит (при равной частоте). Правки инвалидируют только затронутые слои: у каждого слоя свой кэш рендера.
- **Временно включить Draft** с явной пометкой в транспорте.

#### Оставшиеся расхождения (документируются в UI)

- **Частота экспорта отличается от частоты устройства.** Preview звучит на частоте устройства. Для полностью точного прослушивания используется Render Preview, который рендерит на частоте экспорта и ресемплирует результат для вывода. Разница ограничена качеством этого финального ресемплинга.
- **Дизер и кодирование** слышны только в экспортированном файле.

### 4.6 Офлайн-рендер и экспорт

- `OfflineRenderer` выполняет тот же `RenderGraph` в worker-потоке без устройства, с любым целевым sample rate.
- Экспорт: WAV 16/24/32-bit int, 32-bit float, mono/stereo, peak normalization (двухпроходный), TPDF-дизер при понижении разрядности; loudness normalization в Phase 2 вместе с libebur128.
- `af-render` (CLI) рендерит проект без GUI: golden-тесты, batch rendering, проверка воспроизводимости.
- **Воспроизводимость:** собственный PRNG (PCG или xoshiro) и собственные распределения (`std::uniform_*_distribution` даёт разные результаты на разных компиляторах), DSP без `-ffast-math`, `/fp:precise`, версии алгоритмов в проекте.

### 4.7 Импорт больших файлов и AudioBufferCache

#### Политика Phase 1: файл целиком в памяти

Звуковой дизайн работает в основном с короткими файлами, поэтому в Phase 1 ассет полностью декодируется в `float32` с родной частотой файла. Это проще, быстрее и надёжнее потокового чтения. Ограничения:

| Ограничение | Значение по умолчанию | Поведение |
|---|---|---|
| Размер одного ассета после декодирования | **≤ 1 ГБ** (≈ 46 мин стерео 48 кГц, ≈ 23 мин 4 канала 48 кГц) | Больше: импорт отклоняется с понятным сообщением и предложением выбрать фрагмент (импорт диапазона) |
| Предупреждение о размере | > 256 МБ после декодирования | Импорт выполняется, пользователь видит, сколько памяти займёт файл |
| Бюджет кэша (мягкий) | min(40% физической памяти, 80% жёсткого предела), настраивается (ADR-0006) | Выше бюджета вытесняются неиспользуемые ассеты (см. ниже) |
| Жёсткий предел | **min(50% физической памяти, 8 ГБ)**, настраивается | Новые импорты отклоняются, пока память не освобождена |
| Резерв системной памяти | max(1 ГБ, 10% физической памяти), настраивается | Перед каждым декодированием проверяется доступная память системы (`GlobalMemoryStatusEx`): если после выделения останется меньше резерва, импорт откладывается или отклоняется, даже если бюджет AudioForge не исчерпан. По системному уведомлению о нехватке памяти (`CreateMemoryResourceNotification`) вытесняются все вытесняемые буферы |
| Каналы | 1–32 | Клип выбирает каналы: mono, пара, любой канал полифонического WAV (рекордеры Sound Devices, Zoom и др.) |
| Частота | 8–384 кГц | Хранится родная, ресемплинг при воспроизведении (4.5) |
| Форматы Phase 1 | WAV (PCM 16/24/32, float 32/64, BWF, RF64/BW64/W64 — проверено в S1.3, ADR-0012), затем AIFF, FLAC, MP3 | Битые и неподдерживаемые файлы дают ошибку с причиной, приложение не падает |

Сборка только 64-битная.

#### Состояния ассета в кэше

```
Unloaded ──► Decoding (прогресс, отмена) ──► Ready ──► Evicted ──► Decoding ...
                       └──► Failed (причина, повтор)
```

- **Воспроизведение никогда не ждёт декодирования.** Клип, чей ассет не в состоянии Ready, рендерит тишину и показывает на таймлайне индикатор загрузки. Когда ассет готов, граф перекомпилируется.
- **Один проход чтения:** декодирование и расчёт пиков выполняются одновременно.
- **Нехватка памяти при декодировании** (`std::bad_alloc` на worker) ловится, ассет переходит в Failed с понятным сообщением, приложение продолжает работу.
- Учитывается память буферов ассетов, пиков и кэшей Render Preview.

#### Вытеснение

- **Закреплены (не вытесняются):** ассеты, на которые ссылается текущий документ или любой живой граф.
- **Можно вытеснить:** ассеты, на которые ссылаются только записи истории Undo, удалённые клипы, закрытые проекты и предпрослушивание. Вытеснение по LRU.
- Если ссылки остались только у кэша, буфер освобождается на message thread. Если буфер ещё держит граф, он освободится при удалении графа (4.2), то есть тоже не на аудиопотоке.
- Undo, возвращающий клип с вытесненным ассетом, запускает повторное декодирование; клип временно показывает индикатор загрузки.
- Если закреплённые ассеты одни превышают мягкий бюджет, пользователь видит предупреждение «проекту нужно X ГБ, бюджет Y ГБ» с ссылкой на настройку. Работа продолжается до жёсткого предела.

#### Потоковое чтение (Phase 2–3)

Для длинных амбиенсов и полевых записей добавляется второй источник за тем же интерфейсом `ISampleSource`:

- Предзагрузка первых нескольких секунд каждого клипа в память, дальше чтение с диска в отдельном потоке в кольцевые буферы голосов с запасом ≥ 2 с.
- Для сжатых форматов (FLAC, MP3) однократное декодирование в кэш-файл float32 на диске.
- Memory-mapped файлы допускаются только с потоком упреждающего чтения: page fault на аудиопотоке — это блокирующий I/O.
- Нехватка данных в кольцевом буфере (underrun диска) даёт тишину с микро-фейдом и счётчик, а не остановку аудиопотока.

Интерфейс голоса и модель клипа уже в Phase 1 не предполагают, что весь файл в памяти, поэтому переход — замена реализации источника, а не переделка движка.

## 5. Формат проектов и хранение Assets

### 5.1 Проект на диске

Проект — это папка, а не один файл:

```
MyImpact/
├─ MyImpact.afproj          # JSON, вся структура проекта
├─ MyImpact.afproj.lock     # блокировка открытого проекта (pid, машина, время)
├─ Autosave/                # MyImpact.autosave.afproj (ротация 3 копий)
├─ Backups/                 # снимки при каждом ручном сохранении (последние N)
├─ Media/                   # опционально: копии ассетов после «Collect & Save»
├─ Renders/                 # экспорт по умолчанию
└─ Cache/                   # пики, кэши Render Preview; можно удалить, восстановится
```

### 5.3 Точность TimeTicks в JSON

**Проблема.** Стандарт JSON не ограничивает точность чисел, но многие парсеры (JavaScript, часть инструментов, Excel-импорт) читают любое число как IEEE double. Double точно представляет целые только до 2^53 = 9 007 199 254 740 992. При 705 600 000 тиков в секунду это **≈ 12 765 305 с ≈ 147,7 суток**. Значения больше будут молча округлены сторонними инструментами. Вторая опасность — случайная запись времени как дробного числа (`1.5e9`, `1500.0`), после которой точность теряется уже в нашем коде.

**Решение:**

1. **Единицы и диапазоны разделены:**
   - позиция на таймлайне, длины fade, маркеры, loop — `TimeTicks` (int64, 1/705 600 000 с);
   - **позиции внутри исходного файла (`sourceInFrames`/`sourceOutFrames`) — целые сэмплы файла.** Тики делятся без остатка на все стандартные частоты (8–192 кГц и 352,8 кГц), но не на нестандартные (37 800, 384 000, 47 952 Гц и др.). Сэмплы файла точны для любой частоты.
2. **Формат записи:** JSON-целое без дробной части и экспоненты. Писатель сериализует только через int64-путь.
3. **Валидация при чтении (строгая):** значение времени должно быть JSON-целым; дробное число, экспонента, строка или выход за пределы **|x| ≤ 2^53 − 1** — ошибка загрузки с указанием поля (или миграция, если это известный старый формат). nlohmann/json хранит целые как int64/uint64 и проверку позволяет.
4. **Предел модели:** длина таймлайна Event ограничена 24 часами (6,1·10^13 тиков), с запасом в 140 раз до 2^53. Предел проверяется валидатором модели, а не только сериализатором.
5. **`timebase` записан в файле.** Если когда-нибудь понадобится другая единица, это делается миграцией формата, а не догадкой при чтении.
6. **Тесты:** round-trip случайных значений во всём допустимом диапазоне, граничные значения ±(2^53 − 1), отказ на `1.0`, `1e3`, `"123"`, переполнении; проверка, что эталонный проект без потерь читается сторонним парсером на double (скрипт на Python/JS в CI).

**Рассмотренные альтернативы:** строки (`"6585600000"`) точны везде, но неудобны для ручного чтения и легко превращаются в «число в строке» с ошибками; рациональные числа `{num, den}` избыточны; позиции в сэмплах проекта ломаются при смене частоты проекта; double-секунды накапливают ошибку и не дают воспроизводимости.

### 5.4 Sample Browser в Phase 1 (упрощённый)

По решению после версии 0.1 Phase 1 не повторяет «Сэмплотеку». Объём:

- **Папки:** пользователь добавляет папки в список «Избранное»; список хранится в настройках приложения (JSON в `%APPDATA%\AudioForge\settings.json`). Дерево папок и список файлов текущей папки.
- **Файлы:** показываются поддерживаемые аудиофайлы; основные свойства (длительность, частота, каналы, разрядность) читаются из заголовков лениво в фоне, только для видимых строк.
- **Поиск:** фильтр по имени в текущей папке; опционально рекурсивный поиск по имени в фоне с отменой.
- **Предпрослушивание:** Play/Stop, автопрослушивание при выборе, громкость Preview; через Preview-шину движка, старт и остановка без щелчков.
- **Drag & Drop** на таймлайн (новый слой или существующий, несколько файлов сразу), а также из Проводника Windows.

**Не входит в Phase 1:** SQLite-индекс, теги, метаданные BWF/iXML в браузере, UCS-категории, отслеживание изменений папок. Эти функции появятся там, где они нужны (Phase 2+ или через интеграцию с «Сэмплотекой»).

**Интерфейс интеграции сохраняется:**

```cpp
class ILibraryProvider {                        // источник звуков для браузера
public:
    virtual ProviderInfo info() const = 0;
    virtual void browse(const LibraryLocation&, ResultSink<LibraryItem>&, CancelToken) = 0;
    virtual void search(const LibraryQuery&, ResultSink<LibraryItem>&, CancelToken) = 0;
    virtual Result<AssetSource> resolve(const LibraryItem&) = 0;   // в итоге путь к файлу
};
```

В Phase 1 одна реализация, `FileSystemProvider`. «Сэмплотека» подключится второй реализацией (локальный HTTP/named pipe, файл обмена или drag & drop списков файлов) без изменений в браузере и проекте. Жёсткой зависимости нет.

### 5.5 Assets

- **Asset — ссылка, а не копия.** Хранятся абсолютный путь, путь относительно проекта и fingerprint (размер, mtime, xxHash3 содержимого, вычисляется в фоне).
- **Проверка отсутствующих файлов** при открытии: абсолютный путь → относительный → поиск по имени и fingerprint в папках «Избранного». Найденные предлагаются к подтверждению, остальные попадают в диалог **Relink** (один файл или целая папка). Проект с отсутствующими ассетами открывается, клипы показываются как offline и звучат тишиной.
- **Collect & Save:** опциональное копирование ассетов в `Media/`.
- **Пики:** многоуровневые min/max по 256/4096/65536 сэмплов, бинарный файл в глобальном кэше `%LOCALAPPDATA%\AudioForge\Cache\peaks\<xxh3>.afpk`. Ключ — хэш содержимого, поэтому переименование файла не требует пересчёта.
- Поведение в памяти и ограничения размера — раздел 4.7.

### 5.6 Автосохранение, восстановление, бэкапы

- Автосохранение каждые N секунд (по умолчанию 60) при наличии изменений. Неизменяемый снимок документа сериализуется на IO-потоке, UI не блокируется.
- При старте: если найден `.lock` от завершившегося процесса и автосохранение новее основного файла, предлагается восстановление с показом времени обеих версий.
- Бэкапы: копия при каждом ручном сохранении, последние N.
- Crash dumps: минидамп Windows (`MiniDumpWriteDump`) и журнал последних действий в `%LOCALAPPDATA%\AudioForge\Logs`.

### 6.1 Real-time audio

| # | Риск | Последствие | Меры |
|---|---|---|---|
| R1 | Аллокация, блокировка или I/O в audio callback (в том числе скрытые: `std::function`, `push_back`, логирование, освобождение последнего `shared_ptr`) | Dropouts, щелчки, зависания | Правила кода для `engine/rt/`; цепочка владения графом и RetireQueue (4.2); RTSan в Linux CI на каждом PR; debug-хук `operator new` с проверкой аудиопотока на Windows; чек-лист ревью RT-кода |

## 7. Phase 1: вертикальные этапы

### 7.1 Правила

- Phase 1 разбита на **11 вертикальных этапов (S0–S10)**. Каждый проходит через все слои (модель → движок → UI) ровно настолько, насколько нужно для одной новой пользовательской возможности.
- **Каждый этап заканчивается рабочей сборкой:** установщик из CI запускается на Windows 10/11, и в нём можно выполнить сценарий этапа. Сборка этапа помечается тегом `v0.1.0-sN`.
- Задачи этапа (`Sx.y`) — отдельные PR. После каждого PR приложение собирается и запускается.
- **Общий критерий готовности любой задачи:** CI зелёный (Windows MSVC + Linux Clang + RTSan), юнит-тесты на новую логику, нет предупреждений `/W4`, ошибки обрабатываются и показываются пользователю, длительные операции не блокируют UI, новые правки проекта отменяются через Undo (начиная с S3).
- **Критерий готовности этапа:** сценарий этапа выполнен вручную на Windows по чек-листу, найденные блокирующие ошибки исправлены, сборка выложена.

### 7.2 Этапы

#### S0. «Окно» — фундамент и поставка
*Сценарий:* установить AudioForge из установщика, запустить, увидеть тёмное окно с четырьмя панелями-заглушками, открыть About и папку журналов, закрыть.
- **S0.1** Скелет репозитория: CMake + presets, JUCE 8 и зависимости через CPM с фиксированными версиями, clang-format/clang-tidy, модули-заглушки по схеме раздела 2. *Готово:* проект собирается одной командой на Windows и Linux.
- **S0.2** CI: GitHub Actions для Windows и Linux, сборка, тесты, RTSan-конфигурация, артефакты. *Готово:* CI зелёный, артефакт скачивается.
- **S0.3** af_core: UUID, `TimeTicks`, `Result<T, Error>`, логирование в файл. *Готово:* тесты конвертации времени для всех стандартных частот.
- **S0.4** Оболочка приложения: главное окно, тёмный LookAndFeel с дизайн-токенами, панели Left/Center/Right/Bottom с изменяемыми размерами (пока заглушки), меню, About. *Готово:* корректно на 100/150/200% масштаба Windows.
- **S0.5** Диагностика и установщик: минидампы, журнал, Inno Setup (или MSIX). *Готово:* установка и удаление на чистой Windows 10 и 11; искусственное падение создаёт минидамп.
- **S0.6** ADR-0001…0010 в `docs/adr` по принятым решениям.

#### S1. «Услышать файл» — устройство, движок, транспорт
*Сценарий:* выбрать аудиоустройство, открыть WAV через File → Import, нажать Play, услышать, остановить, видеть master-метр. Сменить устройство и buffer size во время воспроизведения без падения.
- **S1.1** RT-примитивы: почтовый ящик, SPSC-очереди, RetireQueue, ParameterBank, triple buffer. *Готово:* стресс-тесты из двух потоков, тесты переполнения по таблице 4.2, RTSan чистый.
- **S1.2** Минимальная модель (Project → Event → Layer → Clip, AssetRef) без Undo. *Готово:* валидация инвариантов.
- **S1.3** Импорт WAV: `IAudioDecoder`, декодирование в фоне в float32, `AudioBufferCache` с состояниями (4.7), проверка RF64/W64. *Готово:* фикстуры всех вариантов WAV; битые файлы дают ошибку; UI не блокируется.
- **S1.4** Движок: `GraphCompiler`, `RenderGraph`, голос клипа с ресемплингом, master, полный механизм передачи графа и забор при остановке устройства. *Готово:* импульс на позиции X звучит ровно на сэмпле X при 44,1/48/96 кГц; независимость от размера блока (бит-в-бит).
- **S1.5** `DeviceService` и диалог Audio Settings (WASAPI), сохранение настроек, обработка пропажи устройства. *Готово:* ручной чек-лист смены устройства, частоты и буфера во время воспроизведения; отключение USB-интерфейса не роняет приложение.
- **S1.6** Транспорт: Play/Stop/Pause, позиция, Space, master-метр. *Готово:* час воспроизведения без xruns на буфере 256.

#### S2. «Собрать слои» — таймлайн и waveform
*Сценарий:* импортировать несколько WAV (меню или перетаскиванием из Проводника), каждый ложится на свой слой, видно waveform, зум и прокрутка, playhead двигается синхронно со звуком, клик по линейке перемещает позицию.
- **S2.1** Кэш пиков (mipmap) в том же проходе, что декодирование; глобальный кэш по xxHash3. *Готово:* совпадение с эталоном; повторное открытие берёт пики из кэша.
- **S2.2** Timeline: строки слоёв, линейка, зум, горизонтальная прокрутка, playhead, виртуализация. *Готово:* 200 клипов прокручиваются плавно (≥ 60 FPS).
- **S2.3** Waveform клипов из mipmap, индикатор загрузки для не готовых ассетов. *Готово:* корректно на всех уровнях зума.
- **S2.4** Drop файлов из Проводника на таймлайн (без браузера). *Готово:* 10 файлов → 10 слоёв.
- **S2.5** Бенчмарк движка с порогом регрессии в CI. *Готово:* базовая линия для 64 слоёв зафиксирована.

#### S3. «Редактировать» — Commands и Undo
*Сценарий:* выделять клипы (в том числе рамкой), двигать между слоями, триммировать, резать, дублировать, удалять, со snap к сетке и без; любое действие отменяется и повторяется; правки во время воспроизведения слышны сразу и без щелчков.
- **S3.1** Неизменяемая модель со структурным разделением, полная версия. *Готово:* тесты разделения узлов.
- **S3.2** Commands, Transactions, UndoHistory, коалесценция жестов. *Готово:* «N случайных команд → N undo → исходный документ»; 100 шагов перетаскивания = 1 запись.
- **S3.3** Выделение, Move, Trim, Split, Duplicate, Delete на таймлайне. *Готово:* каждая операция отменяется.
- **S3.4** Сетка и Snap (включаемый), микро-фейды на границах клипов, кроссфейд графов при структурных правках. *Готово:* нет разрывов сигнала выше порога в тесте правок во время воспроизведения.

#### S4. «Сохранить» — проект на диске
*Сценарий:* сохранить проект, закрыть, открыть снова и получить то же самое; переместить папку с исходниками и восстановить ссылки; недавние проекты.
- **S4.1** Сериализация `.afproj` v1 по разделу 5.2–5.3, строгая валидация времени, каркас миграций, атомарная запись. *Готово:* round-trip; fuzz-прогон; тест со сторонним double-парсером; описание формата в `docs/file-format`.
- **S4.2** New/Open/Save/Save As/Recent, индикатор несохранённых изменений, асинхронное закрытие проекта по 4.2. *Готово:* закрытие во время воспроизведения корректно; вопрос о несохранённых изменениях.
- **S4.3** Offline-клипы, автоматический поиск по fingerprint, диалог Relink. *Готово:* проект с перемещённой папкой ассетов восстанавливается.

#### S5. «Формировать звук» — параметры клипа и слоя
*Сценарий:* настроить у клипа gain, fade in/out с разными кривыми, reverse; у слоя gain, pan, mute/solo, имя и цвет; всё слышно во время воспроизведения и видно на waveform.
- **S5.1** DSP: fades (linear, equal power, exponential, S-curve), clip gain, reverse, constant-power pan, mute/solo с рампой. *Готово:* null-тесты; fade начинается и заканчивается ровно в заданных сэмплах.
- **S5.2** Ручки fade и gain прямо на клипе. *Готово:* одно движение = одна запись Undo.
- **S5.3** Inspector клипа и слоя, групповое редактирование нескольких клипов. *Готово:* изменения слышны без щелчков.
- **S5.4** Создание, удаление, переименование, цвет и порядок слоёв. *Готово:* названия полностью пользовательские.

#### S6. «Свести» — группы, микшер, цепочки эффектов
*Сценарий:* объединить слои в группы (в том числе вложенные), открыть микшер, двигать фейдеры групп и master, видеть метры каждого канала, добавить утилиту Gain в цепочку клипа, слоя или группы и включать bypass.
- **S6.1** Шины групп и маршрутизация по 4.4, правила solo (задокументированы). *Готово:* тесты маршрутизации.
- **S6.2** Инфраструктура цепочек: `IProcessor`, `ProcessorRegistry`, цепочки на трёх уровнях, bypass с кроссфейдом, `NodeStateStore`, PDC, хвосты; утилиты Gain и Polarity/Channel. *Готово:* тест PDC с искусственной задержкой; тест хвоста после конца клипа; смена порядка без щелчков.
- **S6.3** Панель микшера: каналы слоёв, групп и master, фейдеры, pan, mute/solo, метры. *Готово:* синхронизация с таймлайном и Inspector; метры не нагружают UI.
- **S6.4** UI цепочек эффектов в Inspector (добавить, удалить, порядок, bypass). *Готово:* все действия отменяются.

#### S7. «Экспортировать» — рендер, качество, CLI
*Сценарий:* экспортировать Event в WAV с выбором частоты, разрядности, mono/stereo и нормализации; результат совпадает с тем, что звучало в Preview; рендер из командной строки.
- **S7.1** `OfflineRenderer`, экспорт WAV (16/24/32 int, 32 float), peak normalization, TPDF-дизер, длина хвоста, профили экспорта, фоновый экспорт с прогрессом и отменой. *Готово:* исходные файлы и проект не меняются (проверка хэшей в тесте).
- **S7.2** `af-render` CLI и golden-тесты. *Готово:* эталонный проект рендерится в CI и сравнивается с эталоном.
- **S7.3** Режимы качества (4.5): «Как экспорт» по умолчанию, Draft, точный старт, предупреждение о перегрузке. *Готово:* тест «Preview-рендер = экспорт» при равной частоте даёт нулевую разницу.
- **S7.4** Render Preview (точное прослушивание выделенного диапазона). *Готово:* воспроизведение готового буфера, инвалидация при правке слоя.

**После S7 выполнен критерий готовности Phase 1 из ТЗ:** многослойный эффект из нескольких WAV собирается, воспроизводится и экспортируется. S8–S10 доводят Phase 1 до уровня ежедневного рабочего инструмента.

#### S8. «Браузер» — упрощённый Sample Browser
*Сценарий:* добавить папки в Избранное, просматривать файлы, фильтровать по имени, прослушивать, перетаскивать на таймлайн.
- **S8.1** `ILibraryProvider` и `FileSystemProvider`, хранение Избранного в настройках. *Готово:* папка с 10 000 файлов открывается без блокировки UI.
- **S8.2** Панель браузера: дерево папок, список с основными свойствами, фильтр по имени, рекурсивный поиск с отменой. *Готово:* свойства подгружаются только для видимых строк.
- **S8.3** Preview-шина, автопрослушивание, громкость. *Готово:* старт < 50 мс для коротких файлов, остановка без щелчка.
- **S8.4** Drag & Drop из браузера на таймлайн с превью положения. *Готово:* 10 файлов одной записью Undo.

#### S9. «Надёжность» — автосохранение и восстановление
*Сценарий:* принудительно завершить процесс во время работы и при следующем запуске восстановить проект; вернуть предыдущее сохранение из бэкапа; сохранить свою раскладку панелей.
- **S9.1** Автосохранение на IO-потоке, lock-файл, диалог восстановления. *Готово:* после `taskkill` потеря не больше интервала автосохранения.
- **S9.2** Ротация бэкапов и восстановление из бэкапа. *Готово:* восстановление из UI.
- **S9.3** Layout Presets и сохранение настроек интерфейса. *Готово:* раскладка сохраняется между запусками.
- **S9.4** Окно диагностики: загрузка CPU аудиопотока, xruns, `deferredSwaps`, `droppedEvents`, память кэша. *Готово:* счётчики видны и пишутся в журнал.

#### S10. «Кандидат в релиз Phase 1»
*Сценарий:* полный сценарий ТЗ от импорта до экспорта на чистой машине, включая AIFF, FLAC и MP3.
- **S10.1** AIFF и FLAC. *Готово:* фикстуры, тесты.
- **S10.2** MP3 с учётом encoder delay. *Готово:* тест выравнивания с эталонным WAV.
- **S10.3** Ассоциация `.afproj`, `THIRD_PARTY.md`, проверка установщика.
- **S10.4** Приёмка: проект собран, воспроизведён, экспортирован, сохранён, открыт и экспортирован снова, оба экспорта бит-в-бит совпадают; бенчмарк 64 слоёв при буфере 128 укладывается в согласованный бюджет CPU; час работы без xruns и утечек памяти.

### 7.3 Порядок

S0 → S1 → S2 → S3 → S4 строго последовательно: это фундамент, и каждый следующий этап опирается на предыдущий. S5 и S6 можно частично вести параллельно. S8 зависит только от S2 и может идти параллельно S5–S7. S9 можно начинать после S4.

## 8. Процесс разработки и качество

- **ADR** (Architecture Decision Records) для каждого значимого решения: что выбрали, какие были альтернативы, почему.
- **Ветки и PR:** одна задача = один PR, CI обязателен, squash-merge.
- **Тесты:** юнит (Catch2), golden-рендеры через `af-render`, fuzz загрузчика и декодеров, бенчмарки движка с порогом регрессии, RTSan.
- **Чек-лист RT-кода** в `docs/`: что запрещено в `engine/rt/` и как это проверить.
- **Локализация:** все строки UI через `TRANS()`/таблицу строк с первого дня. Архитектура рассчитана на полноценные переводы, в первую очередь **украинский** (затем русский): правила множественного числа CLDR (у украинского и русского четыре формы: one, few, many, other), форматирование чисел, дат и единиц по локали, Unicode-шрифты с кириллицей (включая і, ї, є, ґ), запас места в интерфейсе под длинные строки, переключение языка в настройках, проверка полноты перевода в CI. Подробнее — ADR-0007.

| D11 | Лимиты ассетов (4.7) | **≤ 1 ГБ на ассет после декодирования; мягкий бюджет min(40% RAM, 8 ГБ); жёсткий min(50% RAM, 8 ГБ); резерв доступной системной памяти; все лимиты настраиваются; потоковое чтение в Phase 2–3** | Покрывает типичный звуковой дизайн и не допускает исчерпания RAM. |
| D12 | Формат времени (5.3) | **Тики — JSON-целые в пределах ±2^53, позиции в исходнике — сэмплы файла, строгая валидация, предел Event 24 часа** | Точность в любом JSON-парсере. |

Все решения 9.2 подтверждены 18.11.2026.

### 9.3 Уточнения при согласовании

- **D5:** архитектура локализации должна предусматривать полноценную украинскую локализацию (ADR-0007).
- **D10:** точный старт выполняется автоматически, если укладывается в бюджет подготовки; иначе приложение явно показывает приблизительный старт; Render Preview — гарантированно точное прослушивание (ADR-0005).
- **D11:** жёсткий бюджет изменён с 70% RAM на min(50% RAM, 8 ГБ); учитывается доступная системная память; лимиты настраиваемые (ADR-0006).
- **Процесс:** один PR на задачу, CI и тесты обязательны, переход к следующему этапу только после закрытия критериев готовности текущего.
